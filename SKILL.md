# KiCad engineering workflow

Produce an editable, traceable design supported by evidence. Scale analysis to the circuit and requested change; a small connector edit does not require every specialist review. A clean DRC, attractive render or reference design is not proof of electrical performance.

## Converge to a finished board
Read [convergence](references/convergence.md) before placement/routing of a new or substantially changed board, when resuming unfinished work, and when a session ends with unconnected items. Keep `DESIGN_BRIEF.md` (product use, frozen spec with confirmation dates, user rulings) and `STATUS.md` (main board hash, fresh DRC numbers, next actions) in the project; read both first on resume and verify the hash. Run the feasibility budget before placing parts. While routing, every attempt must improve the fresh DRC metric or be reverted; after two stalled strategies, do not write another router or placer — close the remaining items per net, move the blocking parts, or bring one constraint decision to the user.

## Establish the design
1. Inspect the project, local changes, notes, libraries and generation scripts before editing. Identify the authoritative source and preserve manual edits. Back up substantial changes. Do not upgrade the file format or substitute parts merely to simplify the tools.
2. Establish supply min/nom/max and transients, load continuous/peak/stall and duration, ambient/enclosure, interfaces/edge rates, outline/mounting, layer/cost and assembly constraints. Record known values, sources and material unknowns in the project. Ask only for missing decisions that materially change the design; continue independent work.
3. Before a new placement or substantial redesign, review three perspectives: a first-time nonexpert, the mounted-board operator, and the assembler/rework technician. Establish real use scenarios: installation, all cables attached, programming, operation, power-off and servicing. Verify connector/keying/labels, finger/tool/cable access, mounting hardware, underside clearance, and what switches actually disconnect with battery and USB connected separately or together. Include hand-soldering access, heat delivery, inspection and rework in the assembly review. Use the human-use and assembly sections of [layout and routing](references/layout-routing.md); do not optimize routing before these interactions are resolved. When placing a control or changing its neighboring parts, reserve the actual operating space before packing components and apply the acceptance gate in [control access](references/control-access.md). A body-clearance or DRC pass does not satisfy that gate. For a new architecture or a consequential redesign, compare feasible options using requirements, loss/thermal margin, noise, availability and manufacturing cost. Keep user-selected features. Record the reason for the chosen option before committing the layout.
4. Check installed KiCad version and command help. Find how its Python API runs on this host (system `pcbnew` module, KiCad's bundled Python, or inside a Flatpak with `flatpak run --command=python3 org.kicad.KiCad script.py`). Use tools actually available; inspect API capabilities before scripting. Prefer structured KiCad interfaces over broad text replacements. If editing native files, preserve UUIDs, library identifiers, net assignments and project settings, then reopen them in KiCad. Do not overwrite a GUI session's unsaved work.

## Verify the circuit before layout
5. Within the requested review scope, trace affected supply, load, control and fault paths. Note unrelated risks without expanding the edit scope. Verify symbol pin number → footprint pad → actual package pin, exposed pads, connector mating view, polarity, ratings, logic levels, startup/reset/boot and programming access. Use the exact manufacturer's part/package/revision; read [ee-datasheet-master](../ee-datasheet-master/SKILL.md) when extracting device values. Treat evaluation layouts as package/topology-specific evidence.
6. When the requested change or review affects power, motors, precision analog, fast interfaces, RF or isolation, read the relevant sections of [engineering review](references/engineering-review.md). Show governing equations, units, worst-case inputs and margins. Distinguish calculated, simulated, measured and unresolved results. Do not manufacture a component rating, impedance, current limit or compliance claim.
7. Synchronize schematic and PCB deliberately. Inspect proposed updates before applying them, especially footprint replacement/deletion or re-annotation. Preserve routing/placement and identity unless the requested change needs otherwise. If the schematic is absent, report parity as unverified rather than inventing one.

## Place and route deliberately
8. Read [layout and routing](references/layout-routing.md) for new placement, substantial routing, or SI/PI/EMC/mechanical review. Establish a fab-supported stackup, rule limits and net classes before routing. Separate fabrication minima from chosen design margins; never assume an arbitrary width carries a stated current.
9. Establish a functional floorplan and check routing channels before detailed routing. Place mechanical constraints/connectors first, then critical functional loops, local decoupling and remaining blocks. Review both sides, cable/tool access, enclosure height, antenna restrictions and heat removal. Route constrained nets and their return paths before routine signals. Iterate placement when congestion or return-path problems appear instead of forcing long detours. When the board will not route or many unconnected items remain, read [congestion toolbox](references/congestion-toolbox.md) before changing the router. Review pad-level connectivity and actual filled copper, not only the ratsnest. Update calculations if the final geometry changes the assumptions. For layout optimization, preserve electrical/mechanical constraints and report what improved with before/after evidence.
10. Use [systematic-debugging](../systematic-debugging/SKILL.md) for unexpected behavior, failed checks or tool errors. Reproduce and isolate the cause; do not suppress findings or regenerate away work to force a passing report.

## Verify and hand off
11. Follow [verification and bring-up](references/verification-bringup.md), selecting checks affected by the change. For circuit/layout changes: save/reopen, refill zones, current ERC/DRC, schematic parity when available, and visual inspection of the actual final design. Review warnings, exclusions and remaining unconnected items with reasons. Keep dated reports with the project and rerun affected checks after further edits.
12. For requested production outputs, use [pcb-fab-prep](../pcb-fab-prep/SKILL.md); for requested JLCPCB/LCSC matching, use [jlcpcb-parts-matcher](../jlcpcb-parts-matcher/SKILL.md). Do not treat export as permission to order. Keep source, reports and outputs on the same revision.
13. Distinguish checked fabrication files, a prototype fabrication candidate with disclosed open tests, and a design validated for production. A prototype may be fabricated to resolve documented performance unknowns; do not label it validated. For a new or substantially redesigned board, include a staged bring-up plan with measurable acceptance limits. Physical current, thermal, SI and EMC performance remain unverified until the corresponding measurements are made. Unresolved material connectivity, rating, isolation or manufacturing checks block a production-ready claim, but do not prevent useful draft work.

Report changes, actual checks, material assumptions, blockers and paths concisely. Detailed engineering evidence belongs in the project, not a long chat report. Shared memory writes follow the memory skill's save gate.
